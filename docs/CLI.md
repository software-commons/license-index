# CLI and offline data

Use the launcher from the project where you want to create a license file. Use `--output` with an explicit filename when invoking it from another directory. `text` writes source bytes to stdout. `add --dry-run` writes the preview to stdout. `--json` returns structured UTF-8 to stdout, including the representation, source and output checksums for text operations. CLI errors return exit code 1. Argument errors return 2. Successful calls return 0.

| Command | Result |
| --- | --- |
| `list`, `search QUERY` | List or search names and IDs. Use `--kind license`, `--kind exception`, `--kind other` or `--history` to focus lookup. |
| `show ID` | Machine-readable discovery record, upstream status, artifact locators and coverage information. |
| `show --qualified --policy PATH ID` | Look up an actively selected canonical entity by opaque ID, name or alias using the pinned SCES checkout. Returns the entity and incoming local relationships with their owning entity IDs. |
| `text ID` | Exact pinned bytes from the publisher package, or from a checksum-verified SPDX artifact. |
| `add ID` | Write only the selected LICENSE file, using an explicitly supported installation recipe. |
| `explain ID` | Brief, detailed and scenario-level provisional research with sources, where available. |
| `compare ID ID ...` | Compare cited dimensions, including unresolved fields. |
| `sources ID` | Upstream location, byte fingerprints, archived discovery origins and explanation citations. |
| `coverage` | Report catalog, text, installation and research counts. A checkout with an active publication requires `--policy PATH` for checked selection counts. |
| `review-plan [ID ...]` | List provisional facets, source leads and draft fingerprints for [claim-by-claim review](PROFILE_QUALIFICATION.md). Add `--admission` to plan source and identity review for catalog candidates, including entries without a profile. |
| `expression EXPRESSION` | Parse SPDX 3.0.1 syntax and show unresolved document-local references. |
| `export --qualified --policy PATH` | Export the active qualification report, canonical entities and scoped claims using the pinned SCES checkout. |
| `--version` | Print the software version. |

The text command prefers a bundled publisher file when available. The CLI verifies the admitted edition and SHA-256 before returning or installing a bundled file. Other SPDX-listed texts can be read from a local copy of the pinned upstream data via `--artifact-root PATH`. `--fetch` makes a single explicit request for the cataloged SPDX artifact and verifies its length and SHA-256 before emitting it. The catalog preserves identifiers for both active and deprecated entries. A deprecated identifier may have SPDX replacement advice in `show` and `sources`. Matching templates have their own artifact references. A generated text file may contain upstream matching markers, as observed for the I2P GPL Java exception, so use its representation label and provenance when deciding how to apply it.

The two PolyForm 1.0.0 recipes return the publisher's exact source Markdown with its original line wrapping. The six Creative Commons 4.0 International licenses use the publisher's English plain-text representation. Inspect `text --json` for the representation, source and digest.

`text GCC-exception-3.1` returns the exact `COPYING.RUNTIME` file from GCC 14.2.0 offline. Applying the exception requires the applicable GPLv3 grant and a notice on the runtime files. The installer accepts standalone license identifiers. [GCC 14.2.0 exception text](https://github.com/gcc-mirror/gcc/blob/04696df09633baf97cdbbdd6e9929b9d472161d3/COPYING.RUNTIME#L7-L14).

The installation command supports exact copies of Apache-2.0, EPL-1.0, and EPL-2.0, and both the `-only` and `-or-later` identifiers for GPL 1.0, GPL 2.0, GPL 3.0, and AGPL 3.0. For each GNU edition, the two identifiers select the same document bytes. State the version choice in a separate, authorized project notice and follow the edition’s application instructions for notices and headers. `add` writes a single file. Use `--output COPYING` for GNU’s conventional filename. [GNU GPLv1 application appendix](https://ftp.gnu.org/pub/gnu/Licenses/gpl-1.0.txt), [GNU application guidance with GPLv3 examples](https://www.gnu.org/licenses/gpl-howto.html).

For either EPL edition, identify the covered Program and its license separately and follow that edition’s §3 for notices and distribution. EPL 2.0’s Secondary License option has separate conditions in §3.2 and Exhibit A. [EPL 1.0](https://www.eclipse.org/org/documents/epl-1.0/EPL-1.0.txt), [EPL 2.0](https://www.eclipse.org/org/documents/epl-2.0/EPL-2.0.txt).

`add` can copy the exact publisher Plain Text for all six Creative Commons 4.0 International variants, as well as the CC0 1.0 Universal text. Use a separate authorized notice or dedication to identify the covered material and the exact instrument. Review the selected variant’s conditions before sharing material, particularly when the choice includes NonCommercial, NoDerivatives or ShareAlike. Set a distinct output path for documentation, data, or assets in a project with separately licensed code. Creative Commons recommends software-specific licenses for source code. Its CC0 guidance for software recommends a `COPYING` or `COPYING.txt` file and separate per-file notices. [Creative Commons application guidance](https://creativecommons.org/faq/#how-do-i-apply-a-creative-commons-license-to-my-material) · [Software guidance](https://creativecommons.org/faq/#can-i-apply-a-creative-commons-license-to-software) · [Publisher text rights](https://creativecommons.org/policies/#cc-licensing-statement) · [CC0 guidance](https://wiki.creativecommons.org/CC0_FAQ).

`add PolyForm-Noncommercial-1.0.0` and `add PolyForm-Small-Business-1.0.0` copy the pinned source Markdown unchanged. Use `--output LICENSE.md` for a Markdown filename. A separate authorized project notice can identify the covered software. When distributing the software, see the Notices section for the terms or official URL and any licensor-supplied `Required Notice:` lines. The permitted purposes and Small Business definition come from the selected license. [Noncommercial terms](https://polyformproject.org/licenses/noncommercial/1.0.0) · [Small Business terms](https://polyformproject.org/licenses/small-business/1.0.0) · [Publisher text rights](https://raw.githubusercontent.com/polyformproject/polyform-licenses/a2316cfa35d3947fdc5af4bcc1f321662bfd79d8/LICENSE.md).

For LGPL 2.0 and 2.1, `text` and `add` use the complete GNU document for the selected edition. The `-only` and `-or-later` identifiers for an edition share the same bytes. State the version choice in a separate authorized project notice, follow the application instructions at the end of the document, and check §6 for distribution of linked works. [GNU Library GPL 2.0](https://ftp.gnu.org/pub/gnu/Licenses/lgpl-2.0.txt), [GNU Lesser GPL 2.1](https://ftp.gnu.org/pub/gnu/Licenses/lgpl-2.1.txt).

GNU FDL 1.1, 1.2, and 1.3 each use one verbatim GNU document across their six current SPDX identifiers. Follow the edition’s Addendum for the covered document’s separate authorized notice. That notice states the version choice and identifies any Invariant Sections, Front-Cover Texts, and Back-Cover Texts. The generic identifiers leave those three features unspecified, `-invariants-` requires at least one, and `-no-invariants-` requires all three absent. Preserve the actual notice when redistributing an existing document. [GNU FDL 1.1](https://ftp.gnu.org/pub/gnu/Licenses/fdl-1.1.txt), [GNU FDL 1.2](https://ftp.gnu.org/pub/gnu/Licenses/fdl-1.2.txt), [GNU FDL 1.3](https://ftp.gnu.org/pub/gnu/Licenses/fdl-1.3.txt), [SPDX variant notes](https://spdx.org/licenses/GFDL-1.3-invariants-only.html).

`text LGPL-3.0-only` and `text LGPL-3.0-or-later` return the exact publisher supplement. `text GPL-3.0-only` returns the incorporated GPLv3 document. GNU recommends including both documents and separate licensing notices when applying LGPL 3.0. Run these commands from a directory you control. [GNU LGPL 3.0](https://ftp.gnu.org/pub/gnu/Licenses/lgpl-3.0.txt) · [GNU application guidance](https://www.gnu.org/licenses/gpl-howto.html#license-files).

```text
license-index add GPL-3.0-only --output COPYING
license-index add LGPL-3.0-only --gplv3-text COPYING --output COPYING.LESSER
```

The first command supplies the incorporated GPLv3 document. Choose `LGPL-3.0-only` or `LGPL-3.0-or-later` in the second command and state that choice in a separate authorized LGPL project notice. The second command checks the GPLv3 companion against the bundled publisher bytes before staging and rechecks it before publishing the supplement at a distinct path. The JSON result includes the verified companion path and SHA-256 in `gplv3_text`. `--dry-run` verifies the companion and emits the supplement preview. The two invocations publish completed files separately and refuse to overwrite by default. If `COPYING` already contains the exact GPLv3 text, start with the second command.

`text MPL-2.0` and `text MPL-2.0-no-copyleft-exception` use the pinned SPDX representation through `--artifact-root` or explicit `--fetch`. The two generated license files share the same body, including both exhibits. The SPDX entries display their separate standard headers. Inspect the actual covered files and their licensing history to identify the applicable notice. When distributing incompatible source under MPL 2.0, ensure the Exhibit B notice is attached to the source separately from its appearance in the common license document. [SPDX standard header](https://spdx.org/licenses/MPL-2.0.html), [SPDX Exhibit B header](https://spdx.org/licenses/MPL-2.0-no-copyleft-exception.html), [Mozilla MPL §10.4 and Exhibits A–B](https://www.mozilla.org/en-US/MPL/2.0/), [Mozilla MPL FAQ Q25](https://www.mozilla.org/en-US/MPL/2.0/FAQ/).

MIT's recipe takes the hash-verified SPDX generated plain text from `--artifact-root` or explicit `--fetch`. It accepts a single-line Unicode holder and an explicit four-digit year and changes only the designated notice line. A preview without MIT fields shows that line with placeholders. Use the recipe to create notices for material you are authorized to license and retain applicable notices on redistributed material. The CLI rejects incomplete pairs and rejects copyright fields for unchanged-copy recipes. [OSI MIT rendering](https://opensource.org/license/mit), [MIT representation and application research](../research/campaigns/educational-research.md#mit).

Only a single current license identifier can select an install recipe. With a compound expression or a standalone exception, inspect the source and determine the applicable documents first. Expression output describes syntax and referenced identities. The meaning of `WITH` depends on the identified exception and the relevant base instrument.

The output parent directory must exist. Linked paths, device names, traversal components and nonregular targets are rejected. The existing target can be previewed without modifying it. New output is published atomically without clobbering an existing entry. On POSIX, creation requires hard-link support in the selected directory. Forced replacement on Linux and macOS requires a readable existing file and filesystem support for atomic exchange. The installer checks the original bytes and metadata before and after exchange. Successful replacement preserves the previous file in private staging and reports its path as `preserved_output` in JSON. If it detects a changed entry, it attempts restoration after checking the published file's identity. An error after exchange reports a recovery path for the preserved file, including the copy moved out of the output path by any restoration.

On Windows, forced replacement first moves the opened regular file to a unique sibling name. The output path can be briefly absent before publication. If another writer occupies the path, the installer preserves that entry and reports the sibling path where the previous file remains. Use a directory you control for license installation.

Profiles and comparisons distinguish permissions, conditions, restrictions, sourced descriptions and questions with unresolved treatment. Patent silence, a blank approval field, and a missing explanation carry no affirmative legal finding. The guides provide educational context. Professional legal advice may be needed for applicability to a project or jurisdiction.
