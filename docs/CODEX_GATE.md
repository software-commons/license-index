# Codex technical review issuer

The candidate issuer implements public pull-request capture, a fresh Codex technical review, and optional issuance of a GitHub App check. The existing approval rules still apply. This code has no authority to merge a pull request, publish a release, or select scientific claims.

## Trust boundary

Deploy an independently reviewed copy on an issuer-controlled runner, outside the candidate repository checkout. Pin the issuer code, Python, Git, Codex CLI, reviewer configuration, and approved model. Set up a private, issuer-owned audit directory. Run the fresh Codex process under a dedicated unprivileged POSIX identity, with its own private home and separate Codex authentication. Verify that this identity cannot read the App signing key, issuer configuration or audit storage, installation credentials, or owner administration credentials. Keep the App signing key in organization-controlled custody. Keep short-lived installation tokens out of review inputs, shell arguments, environment variables, repository secrets exposed to PR jobs, and logs.

The issuer reads the fixed public repository and the open, non-draft PR targeting `main`. GitHub provides the base, head and test-merge commit. For a queued review, it also provides the merge-group workflow runs and a live queue ref. The issuer fetches the selected generated ref into a disposable bare repository with the credential helper and inherited Git configuration disabled. It verifies the fetched commit and ordered parents, reads its exact tree, and fingerprints the complete base-to-candidate binary patch. The issuer reviews those objects without checking out or executing proposed code.

GitHub stores checks against a commit SHA and can use head checks if the PR test merge has none. An already checked test merge could become another PR’s head. The candidate gate therefore relies on a mandatory merge queue. Admission reviews the PR test merge and writes an admission check to a single-parent head. Final review fetches the queue's distinct two-parent candidate and verifies that its ordered parents are the current PR base and head. GitHub could use the old result to admit a later PR that reuses a checked commit. Merging that PR requires a final review and CI on its distinct queue commit. A byte-identical regenerated queue commit retains the same GitHub status key.

For the final stage, the issuer requires successful genuine `merge_group` SCES and Domain runs, including all three platform jobs and their corresponding GitHub Actions check records, on that same candidate. The reviewer examines any workflow or validator changes in the exact diff. The issuer rechecks the queue, strict source-bound status rules, PR and queue evidence before issuance and successful completion. Changes to the base, head or queued commit require a new decision.

A new Codex process must return a structured decision after actual diff inspection. The issuer records the run identity, UTC interval, exact snapshot and patch SHA-256, and original trace digest. It verifies a fresh token bound to the verdict, a SHA-256 proof computed from the token and all captured bytes, and actual patch body or mode lines in successful command events. These are mechanical checks. The technical rationale and trusted review process establish the scope of the substantive review. The issuer accepts only the stream from its pinned launcher. A sufficient technical review covers the exact changes, including workflows, evidence controls, and the integrity of generated records. The issuer records bound findings and inconclusive decisions alongside the original trace and exits with a failure.

When reactivating an inactive publication, the issuer reads and checks each inherited qualification, claims payload, and withdrawal advisory within a per-release byte limit. It follows the exact qualification ancestry and stages only the predecessor at its tip. The staged evidence also has a byte limit. SCES requires a withdrawal advisory for every retained release while the publication is inactive. [Pinned SCES publication validator](https://github.com/software-commons/.github/blob/ab26f278422772f2d9e5d4dd016407d14372a710/tools/sces/validate.py#L747)

## Run before activation

Run this from the protected installation directory. Create the private audit directory before the first run.

```text
python -B -m tools.review_gate inspect 1 --state-dir /protected/codex-review-audit
python -B -m tools.review_gate review 1 --state-dir /protected/codex-review-audit --codex /protected/bin/codex --model APPROVED_MODEL
```

The first command captures the public Git objects and exact patch. The second exercises the reviewer on the local account. Add `--queue-admission` to exercise single-parent head validation. After GitHub produces a live merge-group run, use `--queue-run RUN_ID` to inspect the exact queued candidate and the GitHub CI records.

On the intended issuer host, exercise the protected runtime before App registration or live rule changes.

```text
python -B -m tools.review_gate review 1 --rehearsal-config /protected/config/rehearsal.json --queue-admission
```

Use the same `audit_dir`, `codex`, `codex_sha256`, `model`, `reviewer_uid`, `reviewer_gid`, and `reviewer_home` settings described below. The rehearsal configuration omits `app_id`. This runs the pinned Codex launcher under the dedicated reviewer account with the same staging permissions and network-disabled tool profile used for issuance. The audit record is marked as a rehearsal and the command neither reads a token nor writes a check. Verify the account, file access, and shell network boundaries with synthetic sentinels on the intended host. Inspect the effective model tool inventory with synthetic inputs and confirm it exposes only local inspection tools. The protected GitHub queue trial establishes live enforcement separately.

For issuance, run `python -B -m tools.review_gate review 1 --issuer-config /protected/config/review.json --queue-admission` and then a separate execution with `--queue-run RUN_ID` for the live group. Use an issuer-controlled POSIX account with authority to launch the process under the reviewer identity and assign the input group. Configure `app_id`, `audit_dir`, `codex`, `codex_sha256`, `model`, `reviewer_uid`, `reviewer_gid`, `reviewer_home`, and `commissioning_phase` in that private configuration. The reviewer UID, primary GID, and home must match a dedicated system account. The issuer launches Codex with a minimal environment and no supplemental groups. It stages the public inputs under the root-owned sticky temporary directory and grants the reviewer group read-only access. Use a pinned Codex CLI that supports scoped permissions profiles. Install the issuer-pinned, root-owned License model catalog outside the checkout. It preserves the approved direct shell model and disables its patch, experimental tools, and collaboration capabilities. The issuer checks the catalog digest and model before starting every protected review. On Linux, keep the required bubblewrap helper in a trusted system or issuer-controlled runtime path. The protected profile allows reads of minimal runtime paths, the exact pinned Codex executable, and that run's staged inputs. The executable remains visible when the Linux sandbox invokes it inside its namespace. The shell runs with network access disabled. The issuer also disables connected apps, plugins, web search, browser and computer use, image tools, subagents, goals, and interactive user-input tools for the protected launch. The trace validator rejects tool events outside the local inspection profile. Verify these boundaries on the actual host before commissioning.

Protected review stages a copy of the public SCES workflow and validator, SCES-1.0, and SCIRS-1.0 from an issuer-pinned policy bundle outside the checkout. The audit records the exact policy manifest, and the reviewer must prove inspection of the staged policy bytes separately from any selected SCES publication evidence.

A candidate with multiple incoming coverage snapshots also supplies a protected read-only Git object archive. The operator builds it from the exact live head and trusted base and stores it as `HEAD.zip` beside `HEAD.json` in `/opt/software-commons-review/license-review-history-v1`. The private receipt identifies the repository, base, head, archive size, and SHA-256. The issuer binds its hash and ancestry, and the reviewer verifies the intermediate snapshot trees without checking out or executing their contents. The history proof is separate from the standards and publication evidence proofs.

The protected configuration selects one commissioning phase. Set `trial` for the isolated `codex-gate-trial` copy with Code Owner review disabled and zero ordinary approvals. Set `additive` on `main` while ruleset `27875276` requires Code Owner review and one ordinary approval. After authorized cutover, set `final` on `main` with numeric `authorized_cutover_ruleset` set to `27875276`, Code Owner review disabled, and zero ordinary approvals. The issuer binds the observed PR rule and phase to the review record and checks the same requirements again before posting and completing the check. Its owner GitHub CLI session uses read-only API calls for protection and target observations.

For changes to the protected workflow, evidence, tooling, or publication paths on `main`, receive separate owner authorization and pin the exact candidate SHA in the protected `authorized_control_merge` setting. Every `.gitattributes` file under `sces/` is protected because it can affect the bytes Git retains for evidence. Queue admission uses the test-merge SHA. Final review requires authorization for the live merge-group SHA. The issuer records the changed paths and supplied authorization in its audit and requires an exact match before reviewer launch or token access. Apply the trial's existing commissioning authorization to the isolated trial. This control authorization covers the reviewed change. Public dataset release requires the separate exact-artifact authorization.

The config and audit locations are outside Git working trees and owned by the issuer. Their ancestor directories must prevent another account from replacing the private files or directories. The issuer verifies the launcher path and hash before review. A protected credential provider streams a short-lived installation token on standard input. Before either updating a prior check or creating a new one, the issuer verifies that the token's complete repository listing contains exactly the expected repository name and numeric ID. A first issuance reads the token after a complete approval and fresh GitHub read. The issuer creates an in-progress check, verifies the App ID and target, and repeats the relevant checks before completing it successfully. The check and protected record distinguish admission from final review. [GitHub installation repository listing](https://docs.github.com/en/rest/apps/installations#list-repositories-accessible-to-the-app-installation)

Use the same protected audit directory for all issuers writing a given repository and check context so they share the writer lock. Before repeating a review on the same commit, the issuer reads the complete history for the exact App, context, and applicable head or merge-group commit. It preserves the prior check receipts, changes each completed passing check to failure, and confirms that no passing check remains before launching the isolated reviewer. GitHub treats `success`, `neutral`, and `skipped` as passing. A new review approval requires `success`. The isolated reviewer has no access to the installation token. [GitHub required check conclusions](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) · [GitHub check-run updates](https://docs.github.com/en/rest/checks/runs#update-a-check-run)

The issuer authenticates the current pull, review phase, ordered Git parents, and scoped App before supersession. It enumerates all matching check suites and all check runs in each suite. It retires prior passing checks once the exact target and any supplied Git pins are authenticated. That happens before the issuer evaluates eligibility for a new approval, including GitHub mergeability, live branch rules, CI, evidence, and owner authorization. If Git can no longer prove a supplied pin, the issuer rejects the operation. To revoke an older approval independently, run the protected review command for the same phase with `--revoke-only --expected-merge EXACT_SHA`. Supply the test merge SHA for admission or the live merge-group SHA for final review. The issuer records the authenticated target, prior checks, and completed revocations in its protected audit directory. A fresh protected review and the applicable checks are required for a new approval.
