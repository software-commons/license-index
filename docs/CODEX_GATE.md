# Codex technical review issuer

The candidate issuer implements public pull-request capture, a fresh Codex technical review, and optional issuance of a GitHub App check. The existing approval rules still apply. This code has no authority to merge a pull request, publish a release, or select scientific claims.

## Trust boundary

Deploy an independently reviewed copy on an issuer-controlled runner, outside the candidate repository checkout. Pin the issuer code, Python, Git, Codex CLI, reviewer configuration, and approved model. Set up a private, issuer-owned audit directory. Run the fresh Codex process under a dedicated unprivileged POSIX identity, with its own private home and separate Codex authentication. Verify that this identity cannot read the App signing key, issuer configuration or audit storage, installation credentials, or owner administration credentials. Keep the App signing key in organization-controlled custody. Keep short-lived installation tokens out of review inputs, shell arguments, environment variables, repository secrets exposed to PR jobs, and logs.

The issuer reads the fixed public repository and the open, non-draft PR targeting `main`. GitHub provides the base, head and test-merge commit. The issuer fetches the generated merge ref into a disposable bare repository with the credential helper and inherited Git configuration disabled. It verifies the fetched commit and ordered parents, reads its exact tree, and fingerprints the complete base-to-merge binary patch. No proposed source code is checked out or executed.

A new Codex process must return a structured decision after actual diff inspection. The issuer records the run identity, UTC interval, exact snapshot and patch SHA-256, and original trace digest. It verifies a fresh token bound to the verdict, a SHA-256 proof computed from the token and all captured bytes, and actual patch body or mode lines in successful command events. These are mechanical checks. The technical rationale and trusted review process establish the scope of the substantive review. The issuer accepts only the stream from its pinned launcher. A sufficient technical review covers the exact changes, including workflows, evidence controls, and the integrity of generated records. Bound findings and inconclusive decisions are recorded alongside the original trace, and the process returns failure before reading the installation token.

## Run before activation

Run this from the protected installation directory. Create the private audit directory before the first run.

```text
python -B -m tools.review_gate inspect 1 --state-dir /protected/codex-review-audit
python -B -m tools.review_gate review 1 --state-dir /protected/codex-review-audit --codex /protected/bin/codex --model APPROVED_MODEL
```

The first command captures the public Git objects and exact patch. The second exercises the reviewer without contacting the write endpoint or applying the protected issuer's POSIX identity and permissions profile.

For issuance, run `python -B -m tools.review_gate review 1 --issuer-config /protected/config/review.json` from an issuer-controlled POSIX account with authority to launch the process under the reviewer identity and assign the input group. Configure `app_id`, `audit_dir`, `codex`, `codex_sha256`, `model`, `reviewer_uid`, `reviewer_gid`, and `reviewer_home` in that private configuration. The reviewer UID, primary GID, and home must match a dedicated system account. The issuer launches Codex with a minimal environment and no supplemental groups. It stages the public inputs under the root-owned sticky temporary directory and grants the reviewer group read-only access. Use a pinned Codex CLI that supports scoped permissions profiles. The protected launch uses strict configuration and an ephemeral session, grants tool reads to minimal runtime paths and that run's staged inputs, and disables tool network access. Verify these boundaries on the actual host before commissioning.

The config and audit locations are outside Git working trees and owned by the issuer. The issuer verifies the launcher path and hash before review. A protected, nonlogging credential provider streams a short-lived installation token on standard input. The issuer reads it after a complete approval and fresh GitHub read. It creates an in-progress check, verifies the App ID and target, then re-reads the PR before completing the check successfully. It targets only the exact GitHub-generated test-merge SHA.

## Owner activation

1. Register a private Software Commons GitHub App, install it only on License Index, and configure the isolated runner and signing-key custody. Grant repository Checks and Commit statuses write for the App check and its expected-source ruleset binding. Grant the default Metadata read permission. The App needs no code-write, administration, release, merge, or bypass authorization. [GitHub App registration](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app), [expected check source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging).
2. Demonstrate the exact App check on a reviewed GitHub-generated candidate. Keep the existing approval requirements active. Add the App check as a separate required context using its numeric integration ID, keeping the existing required checks and strict branch rules.
3. Demonstrate acceptance of the correct source and commit, and rejection of missing or failed review, fabricated verdicts, same-name checks from other sources, and head or base changes without a new review. Cover retargeting and base-only changes. Verify that GitHub accepts both existing required checks and the App check together, and verify the integrated tree using each permitted merge method. The current Actions checks have been observed on the head SHA. GitHub's rules may prioritize a test-merge check over a head check, so head-only CI cannot be assumed to satisfy this combination. If needed, evaluate a mandatory merge queue with no bypass and final review on its exact merge-group commit as a separate protected design. The current issuer has no merge-queue adapter. [GitHub check placement](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).
4. Record the live control tests and review of the issuer configuration. Replace the approving-review and code-owner requirements only after the authenticated control is enforceably equivalent. Preserve mandatory pull requests, required SCES and registry validation, cross-platform checks, and protections against deletion, force-push and bypass. Keep a separate release-authorization decision.

From the reviewed issuer-controlled copy, the owner can run `python -B -m tools.review_commission --gh-owner --pull 1` to obtain a read-only report keyed to the current GitHub snapshot. After provisioning, use `--app-id ID --decision-sha256 SHA256` to compare the expected source and the exact protected decision. To verify the installation token's observed repository scope, add `--installation-token-stdin` and stream the short-lived token from the protected provider. The report checks active settings and visible results on the raw head and test merge. It requires the App and both CI successes on the same test merge before reporting `matching-observations`. The separate live enforcement trial and owner decision still control cutover.
