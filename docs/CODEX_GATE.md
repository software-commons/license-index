# Codex technical review issuer

The candidate issuer implements public pull-request capture, a fresh Codex technical review, and optional issuance of a GitHub App check. The existing approval rules still apply. This code has no authority to merge a pull request, publish a release, or select scientific claims.

## Trust boundary

Deploy an independently reviewed copy on an issuer-controlled runner, outside the candidate repository checkout. Pin the issuer code, Python, Git, Codex CLI, reviewer configuration, and approved model. Set up a private, issuer-owned audit directory. Run the fresh Codex process under a dedicated unprivileged POSIX identity, with its own private home and separate Codex authentication. Verify that this identity cannot read the App signing key, issuer configuration or audit storage, installation credentials, or owner administration credentials. Keep the App signing key in organization-controlled custody. Keep short-lived installation tokens out of review inputs, shell arguments, environment variables, repository secrets exposed to PR jobs, and logs.

The issuer reads the fixed public repository and the open, non-draft PR targeting `main`. GitHub provides the base, head and test-merge commit. For a queued review, it also provides the merge-group workflow runs and a live queue ref. The issuer fetches the selected generated ref into a disposable bare repository with the credential helper and inherited Git configuration disabled. It verifies the fetched commit and ordered parents, reads its exact tree, and fingerprints the complete base-to-candidate binary patch. The issuer reviews those objects without checking out or executing proposed code.

GitHub stores checks against a commit SHA and can use head checks if the PR test merge has none. An already checked test merge could become another PR’s head. The candidate gate therefore relies on a mandatory merge queue. Admission reviews the PR test merge and writes an admission check to a single-parent head. Final review fetches the queue's distinct two-parent candidate and verifies that its ordered parents are the current PR base and head. GitHub could use the old result to admit a later PR that reuses a checked commit. Merging that PR requires a final review and CI on its distinct queue commit. A byte-identical regenerated queue commit retains the same GitHub status key.

For the final stage, the issuer requires successful genuine `merge_group` SCES and Domain runs, including all three platform jobs and their corresponding GitHub Actions check records, on that same candidate. The reviewer examines any workflow or validator changes in the exact diff. The issuer rechecks the branch rules, PR and queue evidence before issuance and successful completion. Changes to the base, head or queued commit require a new decision.

A new Codex process must return a structured decision after actual diff inspection. The issuer records the run identity, UTC interval, exact snapshot and patch SHA-256, and original trace digest. It verifies a fresh token bound to the verdict, a SHA-256 proof computed from the token and all captured bytes, and actual patch body or mode lines in successful command events. These are mechanical checks. The technical rationale and trusted review process establish the scope of the substantive review. The issuer accepts only the stream from its pinned launcher. A sufficient technical review covers the exact changes, including workflows, evidence controls, and the integrity of generated records. Bound findings and inconclusive decisions are recorded alongside the original trace, and the process returns failure before reading the installation token.

## Run before activation

Run this from the protected installation directory. Create the private audit directory before the first run.

```text
python -B -m tools.review_gate inspect 1 --state-dir /protected/codex-review-audit
python -B -m tools.review_gate review 1 --state-dir /protected/codex-review-audit --codex /protected/bin/codex --model APPROVED_MODEL
```

The first command captures the public Git objects and exact patch. The second exercises the reviewer without contacting the write endpoint or applying the protected issuer's POSIX identity and permissions profile. Add `--queue-admission` to exercise single-parent head validation. After GitHub produces a live merge-group run, use `--queue-run RUN_ID` to inspect the exact queued candidate and the GitHub CI records.

For issuance, run `python -B -m tools.review_gate review 1 --issuer-config /protected/config/review.json --queue-admission` and then a separate execution with `--queue-run RUN_ID` for the live group. Use an issuer-controlled POSIX account with authority to launch the process under the reviewer identity and assign the input group. Configure `app_id`, `audit_dir`, `codex`, `codex_sha256`, `model`, `reviewer_uid`, `reviewer_gid`, and `reviewer_home` in that private configuration. The reviewer UID, primary GID, and home must match a dedicated system account. The issuer launches Codex with a minimal environment and no supplemental groups. It stages the public inputs under the root-owned sticky temporary directory and grants the reviewer group read-only access. Use a pinned Codex CLI that supports scoped permissions profiles. The protected launch uses strict configuration and an ephemeral session, grants tool reads to minimal runtime paths and that run's staged inputs, and disables tool network access. Verify these boundaries on the actual host before commissioning.

The config and audit locations are outside Git working trees and owned by the issuer. The issuer verifies the launcher path and hash before review. A protected, nonlogging credential provider streams a short-lived installation token on standard input. The issuer reads it after a complete approval and fresh GitHub read. It creates an in-progress check, verifies the App ID and target, and repeats the relevant checks before completing it successfully. The check and protected record distinguish admission from final review.

## Owner activation

1. Register a private Software Commons GitHub App, install it only on License Index, and configure the isolated runner and signing-key custody. Grant repository Checks and Commit statuses write for the App check and its expected-source ruleset binding. Grant the default Metadata read permission. The App needs no code-write, administration, release, merge, or bypass authorization. [GitHub App registration](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app), [expected check source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging).
2. Test an equivalent protected trial while the existing requirements on `main` stay active. Configure a mandatory queue with Merge and checks required for every entry. Set build concurrency and the minimum and maximum merge-group sizes to one. Bind all required contexts to their exact numeric App IDs. Retain required pull requests, the strict CI settings, deletion and force-push protection. Verify the complete bypass lists using an owner session. The issuer checks the public active rules. GitHub limits who can see bypass actors in the API. [Branch rules API](https://docs.github.com/en/rest/repos/rules), [merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).
3. Show that head checks permit admission only and that GitHub requires the final App and CI successes on the exact group commit. Exercise missing, failed, fabricated, stale and wrong-source decisions. Cover a changed head, a changed base already contained in the head, retargeting, a removed or replaced queue ref, and reuse of a checked merge object as another PR’s head. Test unauthorized direct updates. Verify the integrated tree against the reviewed group. Confirm that the first queued commit triggers both workflow callers while the initial `main` lacks those files. [GitHub check placement](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [merge-group trigger](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group).
4. Record the live trial and issuer review. Activate the exact equivalent controls before replacing approving-review and code-owner requirements. Preserve mandatory pull requests, required SCES and registry validation, cross-platform checks, and protections against deletion, force-push and bypass. Keep a separate release-authorization decision.

From the reviewed issuer-controlled copy, run `python -B -m tools.review_commission --gh-owner --pull 1` to diagnose the current PR head and test merge. For the mandatory queue, add `--app-id ID --queue-run RUN_ID --admission-sha256 ADMISSION_DIGEST --decision-sha256 FINAL_DIGEST`. This observes both distinct App decisions and the CI results on the head and exact live queued candidate. To check the installation token's observed repository scope, add `--installation-token-stdin` and stream the short-lived token from the protected provider. GitHub may merge immediately after the final check succeeds. Preserve the issuer's pre-completion observations and check receipt, then compare the landed tree, PR timeline and GitHub check IDs with the retained records if the live ref has disappeared. The owner report and live enforcement trial remain separate commissioning records.
